# P10 문제·해설서 — L2 Order Book Replay

**문항 구분:** 실제 기업 기출 원문이 아닌, 호가창 문서·수학·이 프로젝트의 결과를 기반으로 작성한 **기출 유형 연습문제 20개**다. 공개 기출로 오인하지 않는다. 연계: `TEXTBOOK_KO.md`.

## 입문 (Q01–Q05)

### Q01. 호가창과 OHLCV 캔들은 어떻게 다른가?
**해설:** OHLCV는 시간구간 거래가격·거래량 요약이다. L2 호가창은 특정 시점의 가격별 대기 잔량이다. 실제 체결 순서와 queue 우선순위까지 보려면 추가 정보가 필요하다.

### Q02. Bid=99.99, Ask=100.01이면 Mid와 Spread는?
**해설:** Mid=(99.99+100.01)/2=100.00. Spread=0.02. 비율은 `0.02/100×10000=2bp`다.

### Q03. 위 조건에서 즉시 1단위를 시장가성 매수한다면 Mid와의 차이는?
**해설:** 충분한 수량이 있다면 100.01에 매수한다. `(100.01/100−1)×10000=1bp`, 즉 반 스프레드 비용이다. 수수료 5bp를 가정하면 합계 6bp.

### Q04. 최우선 bid 수량 3, ask 수량 1일 때 상단 잔량 불균형은?
**해설:** `3/(3+1)=0.75`. 이 숫자가 상승 확률 75%를 뜻하지 않는다. 예측력이 있는지는 독립적인 실데이터 검증이 필요하다.

### Q05. L2에 주문의 개별 체결 우선순위가 반드시 보이는가?
**해설:** 아니다. 대부분 가격레벨의 합산 물량만 보여준다. 지정가 주문의 선착순 queue 위치를 정확히 알아내려면 체결·주문 수준 데이터와 거래소 규칙이 필요하다.

## 손계산 (Q06–Q10)

### Q06. Ask 100원×2개, 101원×3개일 때 4개 매수의 VWAP는?
**해설:** `(100×2+101×2)/4=100.5`. 주문 수량 4개는 최초 2개를 모두 소진하고 다음 가격에서 2개를 체결한다.

### Q07. 위 호가에서 6개 매수를 요청하면 어떻게 해야 하는가?
**해설:** 표시된 ask 합계가 5개뿐이므로 모델은 `LiquidityError`를 발생시킨다. 부족한 1개를 임의 가격에 체결했다고 가정해서는 안 된다.

### Q08. 결정 당시 Mid=100, 실제 체결 VWAP=100.08, 수수료 5bp이면 체결비용은?
**해설:** 가격비용 `((100.08/100)-1)×10000=8bp`; 총 13bp. 기준이 체결 시각 mid가 아닌 **결정 시각 mid**라는 점이 중요하다.

### Q09. 결정시각 120ms, 가정 지연 100ms, 데이터 이벤트가 10ms 간격이면 어떤 시각의 호가를 사용하는가?
**해설:** 220ms 이상의 최초 이벤트로 주문 체결을 평가한다. 구현상 `bisect_left`로 이 시간을 찾는다. 실제 시스템의 송신·왕복·거래소 처리 지연은 모델링하지 않았다.

### Q10. 매수 체결가 101, 200ms 후 mid 102이면 markout을 어떻게 계산하는가?
**해설:** `(102/101−1)×10000≈99.01bp`. 이는 가상 미래 mid 대비 체결가 변화이고 거래 청산·수수료까지 포함한 실현 PnL이 아니다.

## 데이터 무결성 (Q11–Q15)

### Q11. 현재 `last_id=100`, 메시지가 `[101,105]`를 포함하면 적용할 수 있는가?
**해설:** 새 메시지 ID 구간이 기대치 `101`을 포함하므로 이 모형에서는 적용 가능하다. 적용 뒤 last_id는 105가 된다.

### Q12. 현재 `last_id=100`인데 새 메시지가 `[103,105]`면?
**해설:** 기대 ID 101이 누락되므로 `SequenceGap`을 발생시키고 book을 stale로 표시한다. 이후 새 스냅샷을 얻기 전에는 계산을 멈춘다.

### Q13. 현재 `last_id=100`, 이미 본 `[98,100]`가 도착하면?
**해설:** 최종 ID가 100 이하라 이미 반영된 오래된 메시지로 간주해 `False`를 반환하며 수정하지 않는다. 실제 거래소별 중복·재전송 규칙은 별도로 확인해야 한다.

### Q14. Bid를 101로 고쳤는데 Ask가 100으로 남으면 왜 거절하는가?
**해설:** 최우선 매수가가 최우선 매도가 이상인 crossed book이 되어 정상적인 양방향 표시호가 가정과 충돌한다. 수정 전 사본을 검증한 뒤에만 실제 상태를 교체하도록 했다.

### Q15. 가격을 이진 `float`보다 `Decimal`로 표현한 이유는?
**해설:** 일반적인 소수 가격이 IEEE 부동소수점에서 정확히 표현되지 않아 비교·합산 오류가 생길 수 있다. Decimal도 거래소 틱 크기, 반올림 정책, 수량 제한을 자동으로 보장하지는 않는다.

## 결과·심화 연구 (Q16–Q20)

### Q16. 이 합성 실험에서 0ms 평균 비용은 6.2392bp, 500ms는 12.49767bp였다. 차이는?
**해설:** `12.49767−6.2392=6.25847bp`. 해당 시드·생성규칙·매수방향 조건에서 추가 비용이다. 인과적이거나 실시장 평균이라고 주장하면 안 된다.

### Q17. 600개 증분 메시지가 모두 포함되고 54개 결정 시각마다 지연 4개를 평가하면 주문 예제 총수는?
**해설:** `54×4=216`개다. 600개는 체결건수가 아니라 상태 업데이트 메시지 수다.

### Q18. 수수료 5bp를 0bp로 바꾸면 모든 경우의 계산된 비용이 얼마나 바뀌는가?
**해설:** 계산 정의가 가격비용+고정 5bp이므로 **정확히 5bp 감소**한다. 이는 모델 수수료를 바꾼 민감도 분석이지 거래소 실제 수수료 변화가 아니다.

### Q19. 실거래소 데이터를 사용하기 전에 빠뜨린 필수 테스트 3개는?
**해설:** 예: (1) WebSocket→REST 스냅샷 동기화 중 메시지 버퍼 누락, (2) 접속 끊김/역순 데이터 후 재동기화, (3) 원자료와 재구성한 best bid/ask의 타임스탬프 일치 검증. 추가로 시계동기화·속도 제한·거래소 스키마 버전 확인이 필요하다.

### Q20. 이 실험으로 HFT 수익성이 검증됐다고 주장하는 데 어떤 문제가 있는가?
**해설:** 시세는 합성이고 신호 수익성·반대 주문·실제 거래 API·시장 충격·큐 순서·체결 실패·검증 기간·세금·실제 지연이 없기 때문이다. 구현된 것은 실행비용 **계산 프레임워크의 일부**다.
