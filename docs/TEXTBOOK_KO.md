# P10 교과서 — Order Book Replay Lab

**범위:** 결정론적인 *합성* 호가 데이터를 재생하는 L2 시장 미시구조 연구. 실제 초고빈도 거래 프로그램이 아니다.

## 00. 프로젝트 지도

정해진 시드의 스냅샷과 600개 증분 메시지 → `Book` 객체의 매수·매도호가 구성 → 무결성 검사 → 체결 희망 수량을 여러 가격 레벨에 배분한 VWAP → 의사결정 시각과 가상 주문 도착 시각 비교 → 체결비용(bps)과 표·차트 출력. 코드·로그·원자료는 모두 오프라인이다.

## 01. 산업·학문적 배경

캔들은 일정 시간의 OHLCV 압축 정보다. 반면 호가창은 가격별로 대기 중인 매수·매도 유동성을 나타낸다. 초단기 매매에서는 신호의 방향뿐 아니라 스프레드, 호가 깊이, 지연, 수수료, 체결 확률이 중요하다. P03 Quant Walk-Forward Lab이 시간 단위 전략 검증이었다면 P10은 주문 실행을 위한 **L2 데이터와 비용**을 연구한다.

## 02. 문제·가설

질문 A: 스냅샷 후 증분 이벤트를 순서대로 적용하면 매수·매도 최우선 호가가 올바르게 복원되는가? B: 메시지를 건너뛰면 재동기화가 필요하다고 판정하는가? C: 주문 수량이 최우선 호가 수량보다 클 때 추가 레벨을 사용해 체결단가를 계산하는가? D: 동일 시드에서 가상 지연시간만 바꾸면 어떤 비용 차이가 나타나는가? 실거래 수익성은 연구 대상에 없다.

## 03. 최소 개념

- **Bid / Ask:** 구매 희망자가 제시한 가격 / 판매 희망자가 제시한 가격.
- **Midprice:** `(best_bid + best_ask)/2`.
- **Spread:** `best_ask - best_bid`; 비율은 `spread/mid × 10,000 bps`.
- **L2 depth:** 가격별 총 잔량. 개별 주문 ID나 우선순위가 보통 포함되지 않는다.
- **VWAP:** 여러 가격에서 체결한 물량을 가중한 평균 가격, `Σ(price × executed_qty)/Σexecuted_qty`.
- **Bps:** 1bp = 0.01%. 5bp = 0.05%.
- **호가 업데이트:** 스냅샷은 전체 상태, delta는 해당 가격 레벨의 새 잔량 또는 삭제를 전달한다.

## 04. 선행 시스템

바이낸스의 로컬 호가창 구성 문서는 WebSocket의 depth update와 REST 스냅샷을 일관된 ID로 조합하는 과정을 명시한다. 본 실험은 **시퀀스 연속성 검사라는 핵심 아이디어**를 차용하되 실데이터 연결·버퍼링·거래소별 정확한 필드 프로토콜은 재현하지 않았다. 참고: [Binance Spot Streams](https://github.com/binance/binance-spot-api-docs/blob/master/web-socket-streams.md).

## 05. 설계 결정

가격·수량은 `Decimal`을 사용해 0.01 단위 계산에서 이진 부동소수점 오차를 줄였다. 업데이트 ID 누락 시 `stale=True`를 지정해 잘못된 호가로 계속 분석하지 않도록 했다. 매수·매도쪽 레벨이 교차하면 갱신을 반영하지 않는다. 실제 오더 매칭을 흉내 내지 않고 **즉시 시장가성 주문의 표시 유동성 소진**만 모델링하여 과장된 체결 가정을 피했다.

## 06. 파일·데이터 흐름

`generate`(일회성 합성 데이터 생성) → `replay` → `Book.snapshot`/`Book.apply` → `Book.quote`/`Book.execute` → `measure_latency` → `results/execution_samples.csv` 및 `results/summary.json` → 그림 `latency_cost.png`. `Book.clone`으로 각 시점의 복원된 스냅샷을 따로 보존한다.

## 07. 손계산

Bid=99, Ask=101이면 Mid=100, Spread=2, Spread Bps=200bp. Ask 101에 2개, Ask 102에 3개가 있을 때 3개를 즉시 매수한다면 `(101×2 + 102×1)/3 = 101.3333...`이 VWAP이다. 의사결정 Mid=100 대비 가격 비용은 `(101.3333/100 - 1)×10,000 = 약 133.33bp`다. 여기에 가정한 5bp 수수료를 더하면 약 **138.33bp**. 이는 예시이고, 실제 데모의 호가 간격은 훨씬 작다.

**상단 수량 불균형:** Bid 최상단 잔량 2, Ask 최상단 잔량 3이라면 `2/(2+3)=0.4`. 0.4가 반드시 하락을 예측한다는 뜻은 아니다.

## 08. 코드의 핵심

`normalize()`는 가격·잔량 유효성을 확인한다. `snapshot()`은 최초 ID와 양쪽 호가를 저장한다. `apply()`는 새 이벤트의 ID 범위가 예상 ID를 포함하는지 검사하고 **수정된 복사본**을 검증한 후 상태를 교체한다. `execute('buy',2)`는 가격이 낮은 ask부터 잔량을 사용한다. `measure_latency()`는 의사결정 i에서의 mid와 실행시각 j에서의 VWAP을 비교한다. 동작은 계산만 할 뿐, 실제 자산을 매수하지 않는다.

## 09. 데이터·실험 설정

`generate(seed=17,n=600)`은 10ms 간격으로 중앙 가격을 가상 이동시키고 5단계씩 매수·매도 레벨을 생성한다. JSONL 각 행에 `source: SYNTHETIC`이 표시된다. 54개 결정 시점마다 0/20/100/500ms의 네 가지 지연을 주어 **216개 매수 예제**를 만든다. 주문 크기는 2 가상 단위, 가정 수수료는 5bp이다. 시계열은 약한 상방 편향을 포함하도록 **의도적으로 생성**됐다.

## 11. 테스트

24개 단위 테스트에서 중간가격·스프레드·불균형·매수/매도 VWAP, 유동성 부족, 잘못된 주문, 정상·중복·겹친 업데이트, 시퀀스 누락, gap 이후 중단과 스냅샷 복구, crossed book, 음수 잔량, 시간 역행, 사본 독립성, 데이터 재현성, latency=0의 시각 일치 등을 검증했다. **24/24 PASS**. 이는 실제 거래소 L2와 일치한다는 인증이 아니다.

## 13. 해석과 반증

이 합성 표본에서 500ms 비용이 높은 이유는 가격 생성 과정의 상방 이동과 지연된 ask 체결이 결합됐기 때문이다. **가장 중요한 반증:** 같은 시계열에서 매수 대신 매도하거나 음의 드리프트로 재생성하면 관계가 바뀔 수 있다. 0ms 비용도 0은 아니다. ask를 치는 순간 절반 스프레드·호가 깊이·수수료가 존재하기 때문이다.

## 14. 한계·심화

현재 없는 것: 실제 WebSocket / REST 동기화, 네트워크 시간, 수신 지터, 서명·주문 API, 레이턴시 분포, 실거래 기록, 지정가 체결 우선순위, 취소·숨은 유동성·시장충격, 선물 펀딩·청산. **L2 집계 잔량만으로 자신의 주문이 queue 몇 번째인지 식별하기 어렵다.** 다음 단계는 읽기 전용 실거래소 수집기, 이중 소스 교차검증, 누락 업데이트 재동기화, 이벤트 수신시간과 거래소 이벤트시간의 분리다.

## 15. 면접 설명 기준

**무엇을 만들었는가?** L2 상태 복원과 시장가성 주문의 합성 비용 실험이다. **핵심 버그 유형은?** 누락 메시지 뒤 잘못된 상태로 계속 계산하는 것이다. **무엇을 주장할 수 없는가?** HFT 전략 수익성·실거래 체결 품질·queue position. **확장 아이디어는?** P03 워크포워드 전략의 신호를 실제 L2 읽기 전용 리플레이와 연결하여 지연·수수료·슬리피지에 민감한지 검증한다.

**학습 통과 기준:** 두 레벨을 이용한 VWAP를 손으로 계산하고 `apply`에서 gap 검사를 설명하며 CSV 한 행의 원시 시각·체결가·비용을 재계산한다. 해설형 과제는 `PROBLEMS_SOLUTIONS_KO.md`를 사용한다.
